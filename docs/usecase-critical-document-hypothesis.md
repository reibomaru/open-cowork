# クリティカル資料作成 ユースケース 業務フロー仮説一覧

## 概要

ビジネスサイドから要望として上がった、ビジネス上クリティカルな資料作成のユースケースについて、現時点での業務フロー仮説・不明用語・追加ヒアリング優先度を整理したドキュメント。

これらの資料は**誤りが許されない**性質を持ち、規制対応・経営判断・外部評価に直結するため、自動化にあたっては正確性担保・承認フロー・監査証跡の観点が特に重要となる。

## 2. 不明用語・要確認事項

| 用語/項目 | 仮説 | 確認すべき内容 |
|---|---|---|
| **当局報告の種類** | バーゼル規制関連（自己資本比率等）、業務報告書、マネロン関連報告など複数種類があるはず | ①具体的にどの報告が対象か ②報告頻度（月次/四半期/年次） ③フォーマットは金融庁指定か自由書式か ④電子提出（EDINET/日銀ネット）か紙か |
| **自己査定** | 銀行法に基づく資産の自己査定。債務者を正常先〜破綻先に分類し、引当金を算定する業務 | ①査定の頻度（半期?） ②使用している格付モデル ③査定結果の管理システム ④金融検査マニュアル廃止後の運用変化 |
| **信用格付** | 債務者の信用リスクを評価するスコアリング。内部格付手法（IRB）を採用している可能性 | ①格付モデルは自社開発か外部ベンダーか ②格付の段階数 ③定量/定性の配分比率 |
| **日銀考査** | 日本銀行による金融機関への立入検査。事前に大量の資料提出が求められる | ①直近の考査時期・頻度 ②依頼資料の典型的なボリューム ③過去の考査で指摘された事項 |
| **経営会議の種類** | 取締役会、経営委員会、ALM委員会、リスク管理委員会など複数の会議体がある可能性 | ①対象となる会議体の種類 ②会議ごとの資料フォーマットの違い ③作成頻度 |
| **開示資料** | 有価証券報告書、決算短信、ディスクロージャー誌など | ①どの開示資料が対象か ②EDINET/TDnet提出の有無 ③XBRL対応の要否 |

## 3. 追加ヒアリング優先度

| 優先度 | ユースケース | 理由 |
|---|---|---|
| **高** | 当局報告資料 | 規制要件が厳格で誤りが許されない。自動化範囲の線引き（データ収集まで?転記まで?チェックまで?）が極めて重要 |
| **高** | 審査・与信関係資料 | 与信判断に直結し、誤りが不良債権リスクに直結する。格付モデルの仕様理解が不可欠 |
| **高** | 経営会議資料 | 頻度が高く（月次〜週次?）、多部署からのデータ収集が必要。ROIが高い可能性 |
| **中** | 決算資料 | 業務フローは比較的標準的だが、連結範囲や会計基準の詳細によって要件が大きく変わる |
| **中** | 対顧客提案資料 | 営業現場のニーズが高く頻度も多いが、資料の自由度が高くテンプレート化の難度がある |
| **中** | 外部監査資料 | 資料収集・整理の自動化余地は大きいが、監査対応の時期が限定的 |
| **低** | 内部監査資料 | 監査部門が主管のため、まず業務監査部の協力体制の確認が先決 |

## 4. 横断的な気づき

- **「人間が最終判断、エージェントはドラフト生成まで」の線引きが必須**: これらの資料はすべて、最終的な正確性・判断の責任は人間が負う必要がある。エージェントの役割は「データ収集・集計・ドラフト生成・整合性チェック」までとし、承認・提出は人間が行う設計が前提
- **共通パターン「データ収集 → 集計・加工 → 様式転記 → チェック → レビュー」**: 7つのユースケースすべてがこのパターンに収まる。共通のSkill基盤（データ収集Skill、様式転記Skill、整合性チェックSkill）が設計できる可能性
- **データソースの多様性が最大の課題**: 各資料作成で必要なデータが複数システムに分散しており、API/DB接続/ファイル取得など多様なTool実装が必要
- **監査証跡（Audit Trail）の重要性**: 規制対応資料では「誰が・いつ・何を・どう変更したか」の記録が必須。エージェントの操作ログを監査証跡として保持する仕組みが必要
- **テンプレート管理が鍵**: 当局報告・決算・経営会議などは所定の様式がある。テンプレートのバージョン管理と様式変更への追従が運用上の課題になる
- **業務フロー自動化（前述ドキュメント）との連携**: 定例報告系（ID棚卸し等）の出力がこれらクリティカル資料のインプットになるケースがある。上流の自動化が下流の資料品質に影響する
